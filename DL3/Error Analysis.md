# 機器學習誤差分析 (Error Analysis) 完整筆記

## 1. 什麼是誤差分析 (Error Analysis)？
當您試圖讓機器學習演算法執行「人類可以做到的任務」，但演算法的效能尚未達到人類水準時，**手動檢查演算法所犯的錯誤**能提供接下來該如何改進的寶貴洞察，這個手動檢視的過程就稱為誤差分析。

雖然在機器學習領域中，有時人們會開玩笑地排斥人工介入（hand engineered things）或過多的人為洞察，但在建構實際的應用系統時，這個簡單的計數程序能為您節省大量時間，幫助您決定最重要、最值得專注的優化方向。

---

## 2. 評估單一想法的誤差分析流程
手動誤差分析可以幫助您快速評估一個優化想法是否值得花費數個月的時間去執行。

### 🐱 貓咪分類器範例
假設您的貓咪分類器達成了 90% 的準確度（亦即在開發集 dev set 有 10% 的誤差）。團隊成員發現演算法經常將「狗」誤判為「貓」，並提議花費數個月的時間來收集更多狗的圖片或設計專屬狗的特徵。

#### 分析步驟：
1. **挑選樣本**：從開發集中隨機取出大約 100 個被錯誤分類的樣本。
2. **手動檢查**：逐一檢視這 100 個樣本，並計算其中實際上是「狗」的圖片數量。
3. **評估與決策（設定效能上限 Ceiling on Performance）**：
   - **情況 A（佔比僅 5%）**：若 100 個錯誤樣本中只有 5 個是狗，代表即使您花費數月完美解決了「狗」的誤判問題，誤差也只能從 10% 降到 9.5%。這 5% 的相對降幅通常不值得您投入數個月的努力，這提供了一個效能改進的上限（ceiling on performance），讓您知道最好的情況下能改善多少。
   - **情況 B（佔比高達 50%）**：若錯誤樣本中有 50 個是狗，代表解決狗的問題能讓誤差從 10% 砍半降到 5%。此時投入精力去解決狗的誤判問題就非常值得。

> 💡 **核心價值**：手動檢查 100 個樣本通常只需要 5 到 10 分眾，但這短短的時間能為您提供客觀的估計，避免盲目投入數個月在成效不彰的方向上。

## 3. 平行評估多個優化想法
誤差分析也可以透過建立表格（試算表或普通文字檔），同時平行評估多個改善分類器的想法。

###  平行評估方法
假設您有三個優化想法：改善狗的辨識、改善大型貓科動物（如獅子、豹、獵豹）的辨識、改善模糊影像的辨識。

#### 表格結構範例：
| 影像編號 | 狗 (Dog) | 大型貓科 (Great Cats) | 模糊影像 (Blurry) | 備註 (Comments) |
| :---: | :---: | :---: | :---: | :--- |
| 1 | ✓ | | | |
| 2 | | ✓ | ✓ | 動物園下雨天 |
| 3 | | | ✓ | |
| ... | | | | |

#### 執行與動態調整：
1. **逐一檢視**：逐一檢視錯誤影像，在符合的誤差類別欄位上打勾，並在備註欄寫下簡短註記（例如：「動物園下雨天」）。
2. **動態新增類別**：在分析過程中，如果您突然發現新的錯誤規律（例如：Instagram 或 Snapchat 濾鏡導致誤判），您可以直接在表格中新增一個新欄位，並開始計數。

###  分析結果與決策
在檢視完樣本後，計算每個欄位的打勾比例：
- **假設統計結果**：模糊影像佔 **61%**、大型貓科佔 **43%**、狗僅佔 **8%**。
- **決策依據**：這告訴您，不論在狗或濾鏡問題上做得多完美，效能改進的上限都非常低（約 8% 至 12%）。相反地，改善模糊影像或大型貓科動物的辨識，能帶來顯著更高的效能提升上限。
- **團隊分工**：團隊此時可以根據這些數據，選擇其中一個高潛力方向深入，或者分配不同的團隊同時著手解決這兩大痛點。

## 4. 誤差分析執行要領總結
* **樣本來源**：從開發集（dev set）中找出被錯誤分類的樣本，必須同時包含**偽陽性（false positives）**與**偽陰性（false negatives）**。
* **手動分類與計數**：逐一檢視並統計各類誤差的比例，這能為您提供非凡的啟發，甚至在過程中激發出新的誤差類別與優化靈感。
* **效率第一**：這個快速的程序通常只需要花費幾個小時，卻能幫您與團隊做出明智的資源與任務優先級決策

## 5. 標記錯誤資料（Incorrectly Labeled Data）的處理指南
在機器學習專案中，若發現資料集中存在人類標記人員留下的錯誤標記（Incorrectly Labeled Examples），可以透過以下系統化觀念來評估與處理：

### 5.1 訓練集（Training Set）的處理原則
* **對「隨機誤差」具有魯棒性**：深度學習演算法對訓練集中的**隨機錯誤（Random Errors）**（例如標記人員不小心按錯鍵、分心等）相當強韌。只要總資料量夠大且錯誤率不高，通常可以直接忽略不予處理，演算法仍能正常運作。
* **對「系統性誤差」缺乏魯棒性**：演算法對於**系統性錯誤（Systematic Errors）**非常敏感。例如，如果標記人員持續且一致地將「白色的狗」標記為「貓」，演算法就會學到這個錯誤的規則，將所有白狗分類為貓。這種情況就必須修正。

### 5.2 開發集（Dev Set）與測試集（Test Set）的決策評估
在開發集或測試集中，錯誤標記會直接影響模型的評估。你應該在進行**誤差分析時，額外加入一個欄位，專門記錄「因為標記本身錯誤，導致模型預測與標記不一致」**的數量。

要決定是否值得花時間手動修正開發集的標記，可以比較以下三個指標：
1. **開發集的整體錯誤率（Overall Dev Set Error）**
2. **因標記錯誤導致的誤差佔比（Errors due to incorrect labels）**
3. **因其他原因導致的誤差佔比（Errors due to other causes）**

#### 💡 決策情境對比：
* **情境 A：整體錯誤率高（如 10%）**
  - **數據**：假設整體錯誤率為 10%，其中有 6% 的錯誤是由於標記錯誤所致（即佔整體資料的 0.6%）。這代表因其他原因（如影像模糊、特徵混淆等）造成的誤差佔了 9.4%。
  - **結論**：應優先專注於解決那 9.4% 的其他錯誤來源，修正標記並非當務之急。
* **情境 B：整體錯誤率低（如 2%）**
  - **數據**：假設經過模型優化，整體錯誤率降到了 2%，但標記錯誤造成的誤差仍是整體資料的 0.6%。此時，標記錯誤已佔了所有錯誤的 **30%** ($0.6\% \div 2\%$)，而其他原因造成的錯誤僅剩 1.4%。
  - **結論**：非常值得花時間修正開發集的錯誤標記。因為當你在比較兩個模型（例如錯誤率 2.1% 的模型 A 與 1.9% 的模型 B）時，0.6% 的標記誤差會嚴重干擾評估結果，讓你無法信任開發集的評估效益。

### 5.3 手動修正標記時的三大指導原則
如果您決定要手動重新檢視並修正標記，必須遵守以下原則：
1. **開發集與測試集必須同步處理**：必須對開發集和測試集應用完全相同的修正流程，以確保它們持續來自相同的分佈（Same Distribution），如此開發集的評估結果才能有效泛化到測試集。
2. **同時檢視「猜對」與「猜錯」的樣本**：我們很容易只去檢查模型預測錯誤的樣本，但模型預測正確的樣本中也可能存在標記錯誤（模型可能只是運氣好猜對）。若只修正預測錯誤的樣本，會導致對模型錯誤率的估計產生偏差（給予模型不公平的優勢）。
   > *註：這在實務上並不容易做到。如果模型準確率高達 98%，要檢視 98% 預測正確的標記會花費極大的人力，而檢視 2% 預測錯誤的標記則快得多。因此，這點並不總是會被執行。*
3. **訓練集不一定要同步修正**：由於訓練集通常規模極大，且深度學習演算法對訓練集的隨機誤差有較高的容忍度，因此僅修正較小的開發集和測試集，而保留訓練集中的部分錯誤標記，在實務上是完全可以接受的。

## 6. 實務心態建議
* 許多深度學習研究者傾向於「只將資料餵給演算法，不進行手動干預」。但在建構實務系統時，手動的誤差分析與人類的洞察力往往能帶來極大的價值。
* 不要排斥親自坐下來花幾個小時手動檢視 100 到 200 個錯誤樣本。這種直接觀察資料的過程，能最有效率地幫你釐清專案下一步的優化方向
