## 1. 機器學習基本工作流程與角色定位

在機器學習（Machine Learning, ML）專案中，數據集通常會被劃分為三個核心集合。每個集合在模型開發生命週期中扮演著截然不同且不可替代的角色：

```
                        原始數據集
                       (All Data)
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          Training        Dev          Test
            Set           Set           Set
             │             │             │
             ▼             ▼             ▼
          學習模型       選擇模型        最終評估
          參數           與超參數        泛化能力
```

### 1.1 三大資料集的角色職責

1. **訓練集（Training set）**：
   - **用途**：用來擬合（Fit）與訓練不同的模型參數。
   - **角色**：決定了模型能以多快的速度、以及具備多強的能力去接近與射中目標。

2. **開發集（Dev / Development set，亦稱 Validation set / Holdout cross-validation set）**：
   - **用途**：用來評估不同的超參數（Hyperparameters）、特徵工程策略或模型架構想法。
   - **角色**：作為持續迭代的依據，協助團隊決定 A 方案還是 B 方案更好，直到獲得滿意的分類器表現。

3. **測試集（Test set）**：
   - **用途**：在開發集上選出最終滿意的模型後，用來做最後的系統評估。
   - **角色**：提供無偏差（Unbiased）的效能估計，驗證模型在未見過的數據上的真實能力。

### 1.2 靶心效應（The Target Concept）

* **設定目標**：設定開發集與**單一實數評估指標（Single-number Evaluation Metric）**，就像是在牆上畫下一個明確的「靶心」。
* **團隊特性**：機器學習團隊通常非常擅長朝著設定好的靶心進行優化與迭代。只要靶心明確，團隊就能透過大量的實驗迅速提升指標表現。

## 2. 開發集與測試集分佈對齊（Distribution Alignment）

### 2.1 為什麼開發集與測試集必須來自「相同分佈」？

如果將開發集和測試集設置為不同的數據分佈，就如同讓團隊花了數個月的時間努力瞄準並接近一個靶心，但在最後要測試時，卻突然把靶心移到了別的位置。

* **後果**：數個月的優化努力完全無法轉化為測試集上的實際表現，甚至導致整個系統像紙牌屋一樣崩潰（Collapse like a house of cards）。
* **原則**：**開發集與測試集必須來自完全相同的分佈（Same Distribution）**。

```
[錯誤示範] 靶心位移 (Dev != Test Distribution)
開發集目標 (靶心 A) ------------> 團隊花了 3 個月優化
                                     │
                                     ▼ (部署/測試時)
測試集目標 (靶心 B) <------------ 表現劇烈下滑、系統崩潰

[正確做法] 靶心對齊 (Dev == Test Distribution)
開發集/測試集共享目標 (同一靶心) ===> 優化成果可直接轉化為實際效能
```

### 2.2 錯誤設定的警示案例

#### 案例一：地理區域分佈不均
* **錯誤做法**：將 8 個收集數據的地區中，前 4 個（如 US、UK、Canada、Australia）分配給開發集，後 4 個（如 India、China、Japan、Brazil）分配給測試集。
* **失敗原因**：文化、語言、網路環境與數據特性的劇烈差異，導致開發集的優化經驗無法遷移至測試集。

#### 案例二：貸款預測與收入水平
* **錯誤做法**：某團隊開發貸款審查預測模型時，使用「中等收入郵遞區號」的數據作為開發集進行了數個月的調整，隨後在「低收入郵遞區號」的數據（測試集）上進行最終評估。
* **失敗原因**：收入水平直接影響信用與違約特徵，兩者分佈迥異導致模型表現極差，直接浪費了團隊 3 個月的開發時間。

### 2.3 解決方案：洗牌混合（Shuffle & Mix）

* **做法**：在劃分數據集之前，將所有來源的數據先進行**隨機洗牌（Random Shuffle）**，再分配至開發集與測試集。
* **效果**：確保開發集與測試集同時包含所有地區、所有收入階層或所有數據類型的樣本，讓兩者共享完全相同的混合分佈。

## 3. 大數據時代的數據劃分策略（Data Splitting Strategy）

隨著資料量從早期的千/萬級提升至現代的百萬/億級，數據劃分的經驗法則發生了根本性的轉變。

### 3.1 傳統 ML 與現代 Big Data 劃分比例對比

| 劃分維度 | 傳統機器學習時代（小數據集） | 現代深度學習時代（大數據集 / Big Data） |
| :--- | :--- | :--- |
| **典型數據規模** | 1,000 ~ 10,000 筆樣本 | 1,000,000+ 筆樣本 |
| **常見劃分比例** | **70% / 30%** (Train/Test)<br>**60% / 20% / 20%** (Train/Dev/Test) | **98% / 1% / 1%** (Train/Dev/Test)<br>**99.5% / 0.25% / 0.25%** |
| **核心邏輯** | 樣本量少，需較大比例才能準確評估 | 深度學習極度渴望數據，需將絕大部分留給訓練集 |

```
傳統小數據時代 (e.g. 10,000 筆):
[────── Train (60%) ──────][── Dev (20%) ──][── Test (20%) ──]

現代大數據時代 (e.g. 1,000,000 筆):
[────────────────────────────── Train (98%) ──────────────────────────────][ Dev (1%) ][ Test (1%) ]
                                                                             (10,000筆)   (10,000筆)
```

### 3.2 各資料集的尺寸設定原則

#### 1. 開發集（Dev Set）
* **目的**：評估不同的演算法或模型想法，進行相對優劣排序。
* **大小原則**：只需要**足夠實現評估目的**即可（能顯著區分出方案 A 與 B 的優劣），不需要佔用固定比例（如 20%）。

#### 2. 測試集（Test Set）
* **目的**：評估最終系統的整體效能。
* **大小原則**：應以能**提供高度置信度（High Confidence）**來評估系統效能為準。
* **實務經驗**：在多數應用中，**10,000 或 100,000 筆樣本**就已足夠提供極高的置信度，無需浪費數百萬筆數據於測試集中。

### 3.3 特殊情況：僅使用「訓練/開發集」（No Test Set）

* **現象與定義**：當不需要對最終系統有極高置信度的效能估算時，部分團隊會省略測試集，僅保留 Train / Dev Set。
* **歷史誤區**：許多論文或專案宣稱使用「Train/Test 劃分」，但若在測試集上進行反覆調優（Iterating），該集合實質上已扮演了「開發集」的角色。
* **專家建議**：在大數據集下僅使用 Train/Dev 可能不會引發嚴重過擬合，但保留一個獨立且未曾參與調優的測試集，依然是獲得**無偏差（Unbiased）效能估算**的標準最佳實踐。

## 4. 動態調整評估指標與數據集（Moving the Target）

在專案推進過程中，若發現原先設定的目標位置無法滿足實際需求，就必須果斷地「移動目標（Move the Target）」。

### 4.1 機器學習二步驟哲學（Two Distinct Steps）

機器學習任務應拆解為兩個獨立控制的步驟：

1. **步驟一：設定目標（Placing the target）**
   - 定義出一個能精確捕捉用戶與業務真實偏好的評估指標（Evaluation Metric）。這是最優先的步驟。
2. **步驟二：瞄準與射擊（Aiming and shooting）**
   - 目標設定好後，思考如何讓演算法在該指標上取得好表現（例如：修改神經網路優化的 Cost Function $J$）。

```
[步驟一：設定目標]                                 [步驟二：瞄準與射擊]
定義 Metric & Dev Set                             優化 Cost Function J & 模型架構
       │                                                 │
       ▼                                                 ▼
確定「靶心畫在哪裡」                                 思考「如何精準射中靶心」
```

---

### 4.2 必須調整「評估指標」的情境（案例：色情圖片過濾）

* **背景**：開發貓咪分類器，原使用**分類誤差（Classification Error）**作為指標。
  * **演算法 A**：分類誤差 3%（表現看似較好）。
  * **演算法 B**：分類誤差 5%。
* **衝突**：演算法 A 會不小心讓色情圖片（Pornographic Images）通過；演算法 B 雖然總誤差較高，但完全不會漏過色情圖片。業務需求絕對偏好演算法 B。
* **警訊**：當評估指標無法正確排序（Rank Order）演算法的優劣時，就是必須修改指標的信號。

#### 數學調整方案：引人加權懲罰（Weighted Error）

原本的分類誤差公式對所有錯誤一視同仁：
$$\text{Error} = \frac{1}{m_{\text{dev}}} \sum_{i=1}^{m_{\text{dev}}} \mathcal{L}(y^{(i)}, \hat{y}^{(i)})$$

調整方式：引入權重項 $w^{(i)}$：
$$\text{Error} = \frac{1}{\sum w^{(i)}} \sum_{i=1}^{m_{\text{dev}}} w^{(i)} \cdot \mathcal{L}(y^{(i)}, \hat{y}^{(i)})$$

其中權重設定為：

$$
w^{(i)} =
\begin{cases}
1, & \text{若 } x^{(i)} \text{ 為非色情圖片} \\
10 \text{（或 } 100\text{）}, & \text{若 } x^{(i)} \text{ 為色情圖片}
\end{cases}
$$

* **實務代價**：必須遍歷開發集與測試集，手動標記出色情圖片以進行加權計算。

---

### 4.3 必須調整「開發/測試集」的情境（案例：行動 App 圖片）

* **背景**：演算法 A（3% 誤差）與 B（5% 誤差）是在從網路上抓取的高畫質、構圖完美的圖片（Web Images）上進行評估的。
* **衝突**：實際部署到行動 App 後，用戶上傳的是模糊、低畫質、構圖差的手機照片。在真實應用中，演算法 B 的表現遠優於 A。
* **警訊**：在現有開發/測試集上取得好表現，不等於在實際關心的應用程式中表現良好。
* **調整方法**：重新收集並更換開發/測試集，使其數據分佈精確反映未來實際會遇到的數據類型（例如將模糊的手機照片納入 Dev/Test Set）。

---

### 4.4 團隊實務建議與工程心態

1. **迭代速度（Iteration Speed）是關鍵**：擁有一套評估指標與開發集能讓團隊迅速做出決策（如比較 A 與 B），大幅加快優化循環。
2. **先快速建立，後續再修正**：不必等待完美的指標或數據集才開始。先快速建立第一版以驅動團隊開始迭代，發現不合適再隨時調整。
3. **避免無目標運行**：團隊最忌諱在沒有評估指標與開發集的情況下盲目開發，這會導致研發效率極度低下。

## 5. 總結與黃金法則清單

```
                                黃金法則清單

 1. [分佈對齊] Dev Set 與 Test Set 必須來自完全相同的數據分佈。              
 2. [數據洗牌] 劃分前務必將數據隨機洗牌 (Shuffle)，確保混合均勻。            
 3. [反映未來] Dev/Test Set 的數據類型必須反映實際部署後真正關心的資料。     
 4. [按需分配] 大數據時代下，Dev/Test Set 只需「足夠評估」即可 (如各 1萬筆)。 
 5. [動態修正] 當 Metric 無法正確排序模型優劣時，立即調整指標與 Dev Set。
